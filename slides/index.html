Docker hace lo mismo con el software: un formato estándar que cualquier máquina con Docker sabe ejecutar.

¿Qué es Docker?

Una herramienta para empaquetar una aplicación con todo lo que necesita (runtime, librerías, configuración) en una imagen que corre igual en cualquier lado.

Portable

Corre igual en tu notebook, en el labo y en la nube.

Aislado

Cada app con sus versiones, sin pisarse con otras.

Reproducible

El entorno está escrito en un archivo y se versiona en git.

Docker no inventó los contenedores: los hizo fáciles de usar. Por debajo usa el kernel de Linux:

namespaces

Aislamiento: cada contenedor ve sus propios procesos, red y archivos.

cgroups

Límites: cuánta CPU y memoria puede usar.

capas (union FS)

La imagen se arma en capas apiladas y reutilizables.

Anatomía de docker run

docker run -d -p 8080:80 --name web nginx:alpine
  • Crear y arrancar un contenedor nuevo.
  • detached: corre en segundo plano y nos devuelve la terminal.
  • Publicar puerto host:contenedor. El 8080 de tu máquina va al 80 del contenedor.
  • Nombre para referirnos a él (si no, Docker inventa uno).
  • Imagen a usar. Si no está local, la descarga.
Correrlo y abrir http://localhost:8080. Ojo: si el 8080 está ocupado aparece "port is already allocated": cambiar a -p 8081:80.

Dockerfile v1: la receta

01-capitales-simple/Dockerfile.v1 
# v1: la versión más ingenua (funciona, pero desaprovecha la cache)
FROM node:24-alpine

WORKDIR /app

# Copiamos TODO el proyecto de una vez
COPY . .

# Habilitamos pnpm e instalamos dependencias
RUN corepack enable && pnpm install --frozen-lockfile

EXPOSE 5173

# --host hace que Vite escuche en 0.0.0.0 y no solo en localhost del contenedor
CMD ["pnpm", "dev", "--host"]
  • FROM: imagen base. Node 24 sobre Alpine Linux.
  • WORKDIR: carpeta de trabajo dentro de la imagen (la crea si no existe).
  • COPY: de mi máquina (contexto de build) a la imagen.
  • RUN: ejecuta un comando al construir. Su resultado queda guardado en la imagen.
  • EXPOSE: documenta el puerto. No lo publica: eso lo hace -p.
  • CMD: qué se ejecuta al arrancar el contenedor.

Build & run

01-capitales-simple
docker build -f Dockerfile.v1 -t capitales:v1 .
# -f: qué Dockerfile · -t: nombre:tag · "." = contexto (la carpeta que se envía a Docker)
=> [1/4] FROM docker.io/library/node:24-alpine => [2/4] WORKDIR /app => [3/4] COPY . . => [4/4] RUN corepack enable && pnpm install --frozen-lockfile => naming to docker.io/library/capitales:v1
docker run --rm -p 5173:5173 capitales:v1
# --rm: borrar el contenedor al detenerlo
VITE ready ➜ Local: http://localhost:5173/ ➜ Network: http://172.17.0.2:5173/

¿Por qué --host en el CMD? Vite por defecto escucha solo en el localhost del contenedor, y desde afuera no se llega. Con --host escucha en todas las interfaces.

Probar sacando --host del Dockerfile: el contenedor arranca pero el navegador no conecta. Buen momento para que vean el error.

Cada instrucción es una capa

terminal
docker history capitales:v1
CREATED BY SIZE CMD ["pnpm" "dev" "--host"] 0B EXPOSE [5173/tcp] 0B RUN corepack enable && pnpm insta… 111MB COPY . . # buildkit 23.2kB WORKDIR /app 0B … 8 capas más de node:24-alpine … (~167MB)

Las capas se cachean. Si una cambia, se rehacen ella y todas las de arriba.

FROM node:24-alpine ✔ cache
WORKDIR /app ✔ cache
COPY . . ✘ cambió App.jsx
RUN pnpm install ✘ se rehace (¡lento!)
EXPOSE / CMD ✘

Experimento: cambiar una capital

01-capitales-simple/Dockerfile.v2 
# v2: mismo resultado que v1, pero ordenado para aprovechar la cache de capas
FROM node:24-alpine

WORKDIR /app

RUN corepack enable

# 1) Primero solo los manifiestos: esta capa cambia poco
COPY package.json pnpm-lock.yaml ./

# 2) Instalar dependencias: se reutiliza de la cache si los manifiestos no cambiaron
RUN pnpm install --frozen-lockfile

# 3) Recién ahora el código fuente: cambia seguido
COPY . .

EXPOSE 5173

CMD ["pnpm", "dev", "--host"]
  • Primero solo package.json y el lockfile: cambian poco.
  • La instalación queda en cache mientras no cambien las dependencias.
  • El código va al final: si cambia, solo se rehace esta capa.
.dockerignore 
# Lo que NO queremos mandar al contexto de build
node_modules
dist
.git
Dockerfile*
1) Cambiar "Versión 1" en src/App.jsx y reconstruir v1: pnpm install se repite. 2) Reconstruir v2 dos veces cambiando App.jsx: el install dice CACHED. 3) .dockerignore: sin él, node_modules local (de macOS/Windows) entra al contexto y lo pisa.

Multi-stage: construir con Node, servir con nginx

01-capitales-simple/Dockerfile 
# v3: multi-stage, lista para producción

# ---------- Etapa 1: build (Node + pnpm) ----------
FROM node:24-alpine AS build

WORKDIR /app

RUN corepack enable

COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

COPY . .
# Genera los archivos estáticos en /app/dist
RUN pnpm build

# ---------- Etapa 2: runtime (solo nginx + estáticos) ----------
FROM nginx:alpine AS runtime

# Copiamos únicamente el resultado del build: nada de Node ni node_modules
COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80
# nginx:alpine ya define su CMD, no hace falta repetirlo
  • Etapa build: tiene Node, pnpm y todas las dependencias.
  • pnpm build genera HTML, JS y CSS estáticos en /app/dist.
  • Etapa runtime: arranca de cero desde nginx:alpine.
  • COPY --from=build: se trae solo el resultado. Node y node_modules quedan afuera.

Volúmenes: que los datos sobrevivan

El sistema de archivos de un contenedor es descartable: docker rm y se pierde todo.

terminal
docker volume create pgdata
docker volume ls
Volumen con nombreBind mount
Sintaxis-v pgdata:/ruta-v ./carpeta:/ruta
Dónde viveLo administra DockerUna carpeta de tu máquina
Uso típicoDatos (bases de datos)Código en desarrollo, configs

La base de datos

docker run -d --name db --network capitales-net \ -e POSTGRES_USER=capitales -e POSTGRES_PASSWORD=capitales -e POSTGRES_DB=capitales \ -v pgdata:/var/lib/postgresql \ -v "$(pwd)"/db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro \ postgres:18-alpine
  • Nombre db (será su hostname) y conectado a nuestra red.
  • Variables de entorno: así se configura la imagen oficial de Postgres.
  • Volumen con nombre para los datos.
  • Bind mount del script: todo lo que esté en /docker-entrypoint-initdb.d/ se ejecuta la primera vez.
  • Imagen oficial, versión fija (no latest).
docker exec -it db psql -U capitales -c "SELECT * FROM capitales LIMIT 5;"
En PowerShell usar ${PWD} en lugar de $(pwd). Mostrar que si hacemos docker rm -f db y lo volvemos a crear con el mismo volumen, los datos siguen.

El backend: FastAPI + uv

02-capitales-fullstack/backend/Dockerfile 
# ---------- Base: Python + uv + dependencias ----------
FROM python:3.14-slim AS base

# Traemos el binario de uv desde su imagen oficial (otro uso de multi-stage)
COPY --from=ghcr.io/astral-sh/uv:0.13 /uv /bin/uv

WORKDIR /app

# Primero los manifiestos, para aprovechar la cache de capas
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-install-project

# El virtualenv que creó uv queda primero en el PATH
ENV PATH="/app/.venv/bin:$PATH"

COPY app ./app

# ---------- Dev: recarga automática al cambiar el código ----------
FROM base AS dev
EXPOSE 8000
# --host 0.0.0.0: escuchar fuera del contenedor (por defecto es 127.0.0.1)
CMD ["fastapi", "dev", "app/main.py", "--host", "0.0.0.0", "--port", "8000"]

# ---------- Runtime: producción (target por defecto, es el último) ----------
FROM base AS runtime
EXPOSE 8000
# Forma shell para poder usar $PORT (Render la define); si no existe, 8000
CMD fastapi run app/main.py --host 0.0.0.0 --port ${PORT:-8000}
  • Imagen base oficial de Python, variante slim.
  • Copiamos el binario de uv desde otra imagen: no hace falta instalarlo.
  • Mismo truco de cache: primero pyproject.toml + uv.lock, después uv sync.
  • ENV: variables de entorno de la imagen. El venv queda en el PATH.
  • Etapa dev: fastapi dev con recarga automática.
  • Etapa runtime (la última = la que se construye por defecto). Usa $PORT si existe.

El frontend: Vite + nginx como proxy

frontend/Dockerfile 
# ---------- Base: Node + pnpm + dependencias ----------
FROM node:24-alpine AS base
WORKDIR /app
RUN corepack enable
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY . .

# ---------- Dev: servidor de Vite con recarga en caliente ----------
FROM base AS dev
EXPOSE 5173
CMD ["pnpm", "dev", "--host"]

# ---------- Build: genera los estáticos en /app/dist ----------
FROM base AS build
RUN pnpm build

# ---------- Runtime: nginx sirve los estáticos y hace de proxy a la API ----------
FROM nginx:alpine AS runtime
COPY nginx/default.conf.template /etc/nginx/templates/default.conf.template
COPY --from=build /app/dist /usr/share/nginx/html
# Valores por defecto; se pueden cambiar con -e al hacer docker run
ENV PORT=80
ENV API_URL=http://api:8000
EXPOSE 80
  • Etapa dev: servidor de Vite.
  • Etapa build: genera los estáticos.
  • Etapa runtime: nginx.
  • Template de config de nginx…
  • …con valores por defecto, cambiables con -e.
frontend/nginx/default.conf.template 
# La imagen oficial de nginx reemplaza ${VARIABLES} de este template al arrancar
# y lo guarda como /etc/nginx/conf.d/default.conf
server {
    listen ${PORT};

    root /usr/share/nginx/html;
    index index.html;

    # /api/... se reenvía al backend sin el prefijo /api
    location /api/ {
        proxy_pass ${API_URL}/;
        proxy_ssl_server_name on;
    }

    # Cualquier otra ruta la resuelve React
    location / {
        try_files $uri /index.html;
    }
}

De docker run a Compose: traducción 1:1

Comando

docker run -d --name db \ -e POSTGRES_USER=capitales \ -e POSTGRES_PASSWORD=capitales \ -e POSTGRES_DB=capitales \ -p 5432:5432 \ -v pgdata:/var/lib/postgresql \ -v ./db/init.sql:/docker-…/init.sql:ro \ postgres:18-alpine

La red no aparece: Compose crea una red por proyecto y conecta todos los servicios.

compose.dev.yaml

services: db: image: postgres:18-alpine environment: POSTGRES_USER: capitales POSTGRES_PASSWORD: capitales POSTGRES_DB: capitales ports: - "5432:5432" volumes: - pgdata:/var/lib/postgresql - ./db/init.sql:/docker-…/init.sql:ro volumes: pgdata:

compose.dev.yaml

02-capitales-fullstack/compose.dev.yaml 
# Modo DESARROLLO
#   docker compose -f compose.dev.yaml up --build
# El código se monta desde tu máquina: al guardar un archivo, la app se recarga sola.
name: capitales-dev

services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: capitales
      POSTGRES_PASSWORD: capitales
      POSTGRES_DB: capitales
    ports:
      - "5432:5432"            # expuesto para conectarse con DBeaver/psql desde el host
    volumes:
      - pgdata:/var/lib/postgresql                                # volumen con nombre: los datos persisten
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro    # bind mount: script de carga inicial

  api:
    build:
      context: ./backend
      target: dev              # etapa "dev" del Dockerfile: fastapi dev con recarga
    environment:
      DATABASE_URL: postgresql://capitales:capitales@db:5432/capitales   # "db" = nombre del servicio
    ports:
      - "8000:8000"
    volumes:
      - ./backend/app:/app/app # bind mount del código: los cambios se ven al instante
    depends_on:
      - db

  web:
    build:
      context: ./frontend
      target: dev              # etapa "dev": servidor de Vite
    environment:
      API_PROXY_TARGET: http://api:8000   # Vite reenvía /api/* a este destino
    ports:
      - "5173:5173"
    volumes:
      - ./frontend:/app        # bind mount del código
      - /app/node_modules      # volumen anónimo: conserva los node_modules de Linux de la imagen
    depends_on:
      - api

volumes:
  pgdata:
  • name: prefijo de contenedores, red y volúmenes.
  • Servicio db: el mismo docker run de antes.
  • build en vez de image: construye desde el Dockerfile, etapa dev.
  • El host db = nombre del servicio.
  • Bind mount del código → recarga en caliente.
  • depends_on: orden de arranque.
  • Volumen anónimo para no pisar los node_modules de Linux.
  • Declaración del volumen con nombre.

02-capitales-fullstack/compose.prod.yaml 
# Modo PRODUCCIÓN
#   cp .env.example .env      (y cambiá la contraseña)
#   docker compose -f compose.prod.yaml up --build -d
# Imágenes inmutables, sin código montado, solo el frontend expuesto al exterior.
name: capitales-prod

services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER:?Falta POSTGRES_USER en .env}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Falta POSTGRES_PASSWORD en .env}
      POSTGRES_DB: ${POSTGRES_DB:?Falta POSTGRES_DB en .env}
    volumes:
      - pgdata:/var/lib/postgresql
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    # Sin "ports": la base solo es accesible desde la red interna de Compose
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped

  api:
    build:
      context: ./backend
      target: runtime          # etapa de producción: fastapi run, sin recarga
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
    # Sin "ports": al backend se llega únicamente a través de nginx (/api)
    healthcheck:

⚠️ Plan free: se duerme a los 15 min sin tráfico (la primera visita tarda ~1 min) · la base free vence a los 30 días.

Deploy del ejemplo 1

  1. El código tiene que estar en GitHub (o GitLab / Bitbucket).
  2. Render → New → Web Service → conectar el repositorio.
  3. Language: Docker · Root Directory: 01-capitales-simple
  4. Instance Type: Free
  5. Environment: PORT = 80 → Render espera el 10000 por defecto; nuestro nginx escucha en el 80.
  6. Deploy y mirar los logs: son los mismos pasos de docker build.
  7. Cambiar una capital → git push → redeploy automático. 🎉
Tener la cuenta de Render logueada antes de la clase y el repo ya conectado por si la red está lenta. Guía completa en docs/render.md.
